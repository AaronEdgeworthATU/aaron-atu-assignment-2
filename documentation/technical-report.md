This project uses Terraform and HashiCorp Sentinel, run through HCP Terraform, to enforce digital sovereignty for Ireland and infrastructure security before anything is deployed. Five policies were implemented (sovereignty, encryption, metadata, network and instance_type). A compliant run passed all five policies, and a deliberately non-compliant run was blocked by the hard-mandatory sovereignty policy, with the other policies flagging their failures as advisory warnings.

The biggest limitation is that location is not the same as jurisdiction. Restricting resources to eu-west-1 keeps the data in Ireland, but AWS is a US company and can still be subject to foreign laws such as the US CLOUD Act. Region-based controls show data residency, not full data sovereignty. The policies also only check where resources are created, not where snapshots or backups are copied to later, or where administrators are accessing the data from. The residency check relies on tags as well, which are only as accurate as whoever sets them. In the failed run 11 resources, including route tables, were flagged as holding sensitive data, because the DataClassification tag was applied to every resource through default_tags.

Sentinel only checks the Terraform plan, but things can change between the plan and application. Issues arising outside of Sentinel's control, like someone opening SSH access through the AWS console, can not be caught by Sentinel. Values that are "known after apply", such as IDs and IP addresses, can not be checked at plan time either.

The HCP Terraform free plan also limited the project. Only one policy could be set to mandatory, so the encryption, metadata and network policies could only warn rather than block a run. The policies also had to be pasted into HCP by hand, so the copy in GitHub and the copy in HCP can drift apart if one is changed without the other. For the supply chain, providers are controlled through versions.tf and the .terraform.lock.hcl checksums, but there is no Sentinel policy enforcing this centrally, module code is not checksum verified, and a compromised registry or maintainer account can not be detected by Sentinel.

To improve this, I would recommend using a paid HCP tier, or the API, so the policy set is connected to GitHub and every policy can be set to hard-mandatory. Customer-managed encryption keys, ideally held under EU control, would mean the organisation decides who can decrypt the data, which is a stronger sovereignty control than location alone. Runtime controls should be added alongside Sentinel, such as AWS Service Control Policies to block other regions at the account level and AWS Config to detect changes made outside of Terraform. The DataClassification tag should only be applied to resources that actually store data, such as EBS volumes and databases. A supply chain Sentinel policy and a private module registry could be added to enforce approved provider sources and pinned module versions. Finally, the policies should be reviewed and tested regularly with Sentinel mocks as AWS adds new services, regions and provider versions.
